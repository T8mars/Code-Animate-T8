# 工具手册

《写出来的影像》成片里用户发现、而我们自己没查出来的问题：诡盘转动一卡一卡、小鸟翅膀断线、镜头上下抖、口播串音和漏句。根本原因是只抽看了几张静帧，没看**运动**，也没把成片口播**重新听写**一遍。下面四样工具补上这两个缺口，都在 `template/` 里，一个文件一个工具，文件开头有完整用法。

建议放进工作流程的位置：
- 写完一个镜头 → `contact.js` 看姿态和连续帧（替代只截 5 张静帧）
- 渲染完 → `motion_check.py` 跑整条（或分段列表）
- 口播合成 / 剪完 → `voice_check.py` 对剧本
- 写步进动画、快速旋转时直接用 `lib.js` 的 `stepAt()` / `motionBlur()`

---

## 1. contact.js：镜头接触表

**用途**：把一段时间里的很多帧拼成一张网格图，一眼看出运动是否连贯、角色各个姿态是否有破损（翅膀断线、肢体穿插、偏离画板中心）。

**命令**（在 `template/` 里运行，和 snap.js 一样支持 `PAGE=` `GPU=`）：
```bash
node contact.js out.jpg 2 4 12                       # 2–4 秒之间均匀取 12 帧（对齐到 30fps 帧格）
node contact.js out.jpg 4 - 12 --consecutive --diff  # 从 4 秒起连续 12 帧，每格下面加「和上一格的差异」热度条
node contact.js out.jpg 0.5 2.5 8 --crop 600,200,640,360   # 只看画面里的一块（放大查细线条）
```
选项：`--cols N` 列数（默认自动拼成接近 16:9），`--cell 480` 每格宽度。

**示例输出**：
```
init 55 ms
写出 /tmp/qa/contact_uniform.jpg：12 格（4×3，每格 480×270），帧 60..120，渲染 76 ms/格
f121 Δ17.22  f122 Δ17.29  f123 Δ18.55 ...       （--diff 时逐格打印平均差异）
```
每格左上角黄色标签是「秒数 帧号」；`--diff` 时右上角是和上一格的平均差异（0–255，< 0.3 标红 = 这一帧没变）。

**怎么看**：
- 连续模式里几格完全一样、然后突然跳一大步 = 步进卡顿；画面整体上下错位 = 镜头抖；物体一格跳过自身宽度的一半以上 = 该加 `motionBlur`。
- 细线条（描边剪影、辐条）一定要用 `--crop` 放大看。缩略图里看不出断线。

**已知局限**：
- 速度和 snap.js 一样（模板场景约 80 ms/格，WebGL 重的场景在 SwiftShader 上要 1–3 秒/格）。
- 只能检查确定性的 `renderFrame(t)`：有状态的镜头（粒子、数据混合）跳着取帧时，画面和顺序渲染的结果不同，这种镜头要用 `--consecutive`，或者直接看渲好的 mp4（`ffmpeg -ss 4 -t 0.4 -i out.mp4 -vf "scale=480:-2,tile=4x3" -frames:v 1 sheet.jpg`）。

## 2. motion_check.py：卡顿 / 静止过久 / 镜头抖

**用途**：读渲染好的 mp4，逐帧算相邻帧差和整体位移，报告三类运动问题，以及切镜头的位置。

**命令**：
```bash
python3 motion_check.py out.mp4                          # 整条
python3 motion_check.py out.mp4 --start 100 --end 130    # 一段
python3 motion_check.py ../render/a1/list.txt            # 分段渲染的 ffmpeg concat 列表，不用先拼接
python3 motion_check.py out.mp4 --csv m.csv --json r.json   # 逐帧数据 / 机器可读报告
```
可调：`--static-sec 2.0`（静止多久算过久）、`--static-thr 1.0`、`--move-thr 1.0`、`--jitter-px 1.5`（1080p 像素）。

**示例输出**（故意做坏的测试视频）：
```
motion_check: bad.mp4  1920x1080 @ 30fps，分析 420 帧（0.00s–13.97s）
  帧差中位数 2.14；切镜头 2 处：5.00s, 8.00s
  [卡顿] 0:00.03–0:02.40（f1–f72，2.4s）  全画面：每 4 帧出现一次大跳变（其余帧只有小幅变化），约 7.5 次/秒，均匀步进 → 若非刻意的定格风格，改为每帧一格或加 motionBlur()
  [卡顿] 0:02.40–0:04.83（f72–f145，2.5s）  全画面：每 3/4 帧出现一次大跳变（其余帧只有小幅变化），约 8.0 次/秒，不均匀 → 每秒步数不整除帧率，改用 stepAt()
  [抖动] 0:05.10–0:07.90（f153–f237，2.8s）  竖直位移来回翻转 26 次，最大偏离 8.0px（1080p）；例：f153 -7.9，f156 +7.8，f159 -7.9 …
  [静止过久] 0:08.03–0:10.97（f241–f329，3.0s）  0.5 秒内平均变化 0.44、相邻帧差 0.53（阈值 1.0），画面几乎不动
```
**真实片子上的结果**：
- **r1 备份渲染**（`render_r1bak/`，修复前）：抓到了用户报告的诡盘卡顿，`[卡顿] 全画面：每 3/4 帧出现一次大跳变，约 8.0 次/秒，不均匀`（片中 108–120 秒）；冷开场里的小诡盘也报了同样的 3/4 帧（约 28 秒）。
- **修好后的成片**：同两段没有报告。
- **修好后的成片整条跑一遍**（18 分钟）：
  - 4 条卡顿，其中第一幕结尾的色块 `Math.floor(lt*4)` 是 7/8 帧交替（4 次/秒不整除 30），真实但不显眼。
  - 5 条抖动，全部在默片段（刻意的片门晃动）。
  - 34 条静止过久，多是字卡和尾声的定格画面，按「静止不超过 2 秒」的规则确实超了。
- **文字之城**：在成片里没有报抖动（相机高度已经用预先平滑的曲线）。修复前的版本没留下渲染，这一项只用合成视频验证过。

**判据**（都在 320 宽灰度图上算，胶片颗粒经面积下采样基本被平均掉）：
- **卡顿**：1 秒滑窗内有明显运动，并满足以下两种之一：
  - **停顿型**：≥30% 的帧帧差接近 0，整块画面每 N 帧才更新。
  - **跳变型**：帧差每 2–10 帧出现一次周期性尖峰。诡盘就是这种：小鸟每帧都在拍翅，所以帧差从不为零，但转盘隔几帧跳一步。

  画面分 4×3 个区域各查一遍，所以只占画面一角的步进动画也能抓到。主要间隔是相邻两个整数（3/4、7/8、1/2）的判为**不均匀**（每秒步数不整除 30，一定要修）；单一间隔的判为**均匀**（可能是刻意的定格风格）。
- **静止过久**：和 0.5 秒前那帧相比几乎没变，且连续 ≥2 秒。慢速推拉摇移会累积出差异，所以不会被误报。
- **抖动**：在 4×3 块上各做一次相位相关（numpy FFT），取一致的可信块的中位数作为整体位移。减去 9 帧滑动中位数（去掉正常平移）后，残差超过阈值、且 1 秒内符号翻转 ≥3 次即报。低纹理块（渐变天空、雾、黑底）不参与。

**耗时**：约 0.008–0.015 秒/帧（2 核 CPU，解码占一半）。14 秒测试视频 6 秒，18 分钟成片（31851 帧）3 分 54 秒。

**已知局限**：
- **只认节奏，不认内容**：刻意的效果也会报，核对时间点即可。例如默片段的 16 格/秒（在 30fps 下是 2/2/2/1 帧交替，确实会顿）、默片的片门晃动、冲击震屏、按拍子闪烁。
- **抓不到时间混叠**：快速旋转的辐条轮不加模糊时每帧转过 28°，看着像倒转或频闪，但帧差均匀，不会报。这种要用 contact.js 连续帧去看。
- 抖动检测需要画面里至少 4 块有纹理且一起动。大面积粒子、满屏独立运动的文字、纯色或渐变背景上的抖动测不到。逐帧的 `--csv` 里 `n_conf_tiles` 列是可信块数。
- 静止阈值按本模板的 `post()` 颗粒（约 ±7 级）标定。颗粒很重（如 `grain .15`）时调高 `--static-thr`，否则会漏报静止；画面很暗、几乎无颗粒时可以调低。

## 3. voice_check.py：口播校对

**用途**：用 faster-whisper 把口播重新听写一遍，按拼音和剧本对齐（同音字识别错误不算错），报告以下问题：
- 漏掉的句子
- 音频里多出来的字（重复、串音、旧录音残留）
- 每句首尾是否被切
- 切点没有留白

**命令**：
```bash
python3 voice_check.py script.txt voice_track.wav                 # 一整条口播（或成片导出的音轨）
python3 voice_check.py script.txt voice/lines/                    # 逐句 wav 文件夹（按文件名排序，不要求和句子一一对应）
python3 voice_check.py script.txt voice.wav --terms "鹈鹕,康定斯基,Shadertoy" --cache asr.json --verbose --json r.json
```
剧本一行一句，可写 `L021|句子` 带编号。`--terms` 只给专有名词，**不要把整段剧本当提示词**：识别会照着剧本猜，掩盖真错误。`--cache` 保存听写结果，改剧本后重跑只要 1 秒。

**示例输出**（L021–L025 真实录音故意拼坏：L022 混进旧录音 L019 的半个字并重复「墙边」，漏 L023，L024 切头，L025 切在「影」中间）：
```
voice_check: 剧本 5 句 113 字；音频 4 个文件
对齐：剧本 113 字中 92 字同音匹配，2 字识别成别的字，19 字没有声音；听写多出 2 字
  [多余] 重复「墙边」：第2句[L022] 中间（「画室看见」之后），L022.wav 4.50–4.96s
  [切点贴得太紧] L022.wav（第2句[L022]） 开头 30ms 就有 -16dB 的声音，没有留白 —— 可能切在字中间
  [漏句] 第3句[L023]「走近才认出来：那是他自己的画，只是侧着靠在了墙上。」在音频里找不到（对上 2/22 字）
  [切点贴得太紧] L024.wav（第4句[L024]） 开头 30ms 就有 -6dB 的声音，没有留白 —— 可能切在字中间
  [切点贴得太紧] L025.wav（第5句[L025]） 结尾 60ms 还有 -6dB 的声音，没有留白 —— 可能切掉了尾音
```
同一批坏数据拼成整条 wav 时报出：重复「墙变墙变」（同音，照样算重复）、漏句 L023、`[结尾被切] bad.wav 22.78s 第5句 声音戛然而止`。没报出的见下方局限：L022 头上的旧录音残留、L024 切头。

正常拼接的同一批录音（整条和逐句两种形式）：`没有发现问题。`。其中 3 处同音识别错误（萤幕/银幕、朱镜/走近、美暴露/美爆了）没有误报。

**真实片子上的结果**：
- **成片 r1 的音轨**（带配乐，18 分钟）：抓到了用户报告的「最后一句漏了」：
  ```
  [漏句] 第104句[L104]「我是 T8，我们下期见。」在音频里找不到（同音对上 0/9 字）；那个位置听写到的是「詞曲李宗盛」（片尾音乐的幻听）
  ```
  另外 4 条：
  - L9 后多出「诶」：cuts.py 里正好有一处 L8/L9 切点的手工修正，可能就是它。
  - L102/L103 之间多出「所以」：真实差异，见下一条。
  - 「1980 年代 → 19世纪80年代」「Sora → 索尔」两条是识别错误。

  用户报告的 L22/L24 混进旧 L23 半个字，在整条音轨模式下**没有**抓到（Whisper 不转写半个字）。
- **最终的 104 个逐句文件**（文件夹模式）：报了 7 条，都需要人去听：
  - L103.wav 实际念的是「**所以**别急着**删除**它」（剧本是「别急着删掉它」）
  - L010.wav 开头有 0.7 秒「呵呵」
  - L078 听写里没有「能直接」
  - L060 句中「戛然而止」（逗号处，可能是误报）
  - L007 的「AI」、L044 的「19世纪」、L061 的「Sora」是识别问题
- 句中单个多出的字（的/了/儿）多半是识别加的虚字，只汇总计数，`--verbose` 里列出。

**报告类型**：
- `[漏句]`：对上 <40%（或同音字 <15%），会顺带给出那个位置实际听写到了什么。
- `[多余]`：「重复」= 和紧挨着的字一样；不是重复的 = 串音、旧录音、口误。
- `[开头被切]` / `[结尾被切]`：首尾 1–3 字完全没有声音，或声学上「戛然而止」。
- `[切点贴得太紧]`：逐句文件的首尾没有留白，或整条音轨里两句之间没有停顿。
- `[句中缺字]`
- `[听写不符]`：有声音，但大部分字对不上，需要人去听。

**耗时**：模型加载约 5 秒；2 核、small int8。25 秒口播约 10–17 秒，18 分钟成片音轨 2 分 23 秒，104 个逐句文件（约 8 分钟口播）4 分钟（逐个文件有固定开销）。有 `--cache` 时重跑约 1 秒。

**已知局限**：
- **Whisper 会「顺手修正」单字重复**：「变变魔术」听写成「变魔术」，测试里没抓到。双字以上的重复（「墙边墙边」）能抓到。
- **听不见半个字**：混进来的 0.3 秒旧录音残留，Whisper 往往不转写。这时只能靠声学检查：逐句文件模式下文件开头没有留白会被抓到；整条音轨模式下，残留前后都有停顿就抓不到。所以**优先用逐句文件夹模式**跑一遍，再用整条音轨模式跑一遍。
- **开头被切只靠听写判断**：自然的普通话起音 30ms 内就达到峰值，和硬切分不开，所以没有做声学开头检查。被切掉的部分不到半个字时，Whisper 仍会听写出那个字。结尾的「戛然而止」检查可靠：自然句尾最后 40ms 都在 -16dB 以下，切掉尾音的在 -6dB 左右。
- **配乐响的段落**，识别率会下降，会出现 `[听写不符]`。有配乐时（整条音轨的 5% 分位响度 > -40dB），句间停顿检查自动跳过并给出提示。尽量用干声轨（混音前的口播）跑。
- 数字按逐位读处理（1935 → 一九三五）。剧本写「1935」但念成「一千九百三十五」时会报不符，剧本里改成实际念法即可。

## 4. lib.js：stepAt() 和 motionBlur()

### stepAt(t, fps, stepsPerSec)：离散步进动画的格号
```js
const slot = stepAt(lt, FPS, 30);          // 每帧一格（诡盘：每帧转 30°，小鸟原地拍翅）
const pose = stepAt(lt, FPS, 10);          // 每 3 帧换一个姿态（均匀的定格风格）
stepAt(lt, FPS, 8);                        // console.warn：8 不整除 30，改为 10（每格 3 帧）
```
每秒步数被强制为 fps 的整数约数（30 → 30/15/10/6/5/3/2/1）。不是约数时就近取一个约数（距离相同取较大的）并警告一次。内部用整数帧号计算，不受浮点误差影响。

### motionBlur(drawFn, t, n = 8, shutter = 0.5, o = {})：子帧平均的运动模糊
```js
motionBlur((c, tt) => { c.fillStyle = BG; c.fillRect(x0, y0, w, h); wheel(c, cx, cy, R, spin(tt)); }, t, 12, 0.5, { ctx: CTX });
```
- 在 `[t, t + shutter/30)` 内取 n 个子帧，分别画在离屏画布上，再以 `'lighter'` + `globalAlpha = 1/n` 相加 = 等权平均。不透明画面和透明叠层都正确。
- 返回离屏画布；给 `o.ctx` 时直接画上去。drawFn 没画到的地方是透明的。
- 实测（软件渲染 1920×1080）：n=8 约 40ms，n=16 约 90ms。getImageData 浮点平均分别要 190ms 和 390ms。和精确平均相比，平均误差 0.02 级，最大 2–4 级。
- 什么时候用：物体每帧位移超过自身宽度的一半（快速旋转的轮子、高速诡盘、甩镜头里的物体）。
- 局限：开销 = n 倍的绘制。物体只占画面一小块时用 `o.w/o.h` 开小画布、自己 drawImage 到位置上。子帧数不够时能看到 n 道细纹（n=12 时辐条上隐约可见），这时提高 n。

### 示例：examples/motion_demo_scene.js
3 秒转盘演示，左边是诡盘（`stepAt` 每帧一格），右边是每秒 2.3 圈的辐条轮（`motionBlur` n=12）。地址加 `?bad=1` 是做坏的版本（`Math.floor(t*8)`、无模糊）。
```bash
cp ../examples/motion_demo_scene.js scene.js && node render.js 0 3 demo.mp4 && python3 motion_check.py demo.mp4
PAGE='film.html?bad=1' node render.js 0 3 bad.mp4 && python3 motion_check.py bad.mp4
```
实测：
- 好的版本：`未发现卡顿 / 静止过久 / 抖动`，约 170 ms/帧，motionBlur 占约 100 ms。
- 坏的版本：`[卡顿] 0:00.03–0:02.83 第2排第1列… 每 3/4 帧出现一次大跳变，约 8.0 次/秒，不均匀`。

# 长片骨架与制作工具

下面五样把《写出来的影像》里实际用过、但旧模板没有的做法抽成了模板。原有的 10 秒流程（改 `scene.js` → `snap.js` → `render.js`）完全不变：`film.html` 只多加载了一个 `shots.js`，旧式 `scene.js` 自己定义的 `initFilm`/`renderFrame` 照样覆盖它。实测原示例渲染 10 秒仍是 300 帧、39 秒。

## 5. shots.js：镜头时间线骨架

**用途**：长片只写镜头，不再手写 `renderFrame`。时间点跟着口播句子走，带交叉溶解、每镜头的辉光和颗粒、源码角标，还会检查镜头表。

**写法**（完整示例 `examples/shots_scene.js`，复制成 `scene.js` 即可运行）：
```js
setTimeline({ lines: { 1: [0.6, 2.8], 2: [3.6, 6.0] }, gaps: [[2.8, 3.6, 'breath']] });  // 口播时间表，可省略
filmOptions({ tags: true });                                   // 右上角显示「文件名:行号」
shot(0, LS(2), { draw(ctx, lt, t, f) { ... } });               // lt 镜头内秒，t 全片秒，f 帧号
shot(LS(2), LE(2) + .3, { xin: .5, bloom: .35, grain: .04, state: TRAIL, draw(ctx, lt, t, f, st) { ctx.drawImage(st.cv, 0, 0); } });
onInit(async () => { /* 加载图片、建 WebGL */ });
```

**接口**：
- `shot(a, b, {init, draw, xin, grain, bloom, bthr, state, solid, tag, tagDark, tagA})`
- `LN / LS / LE(id)`：句子起止。id 写 21 或 'L021' 都行。
- `GP(label, after)`：按名字找空档。
- `setTimeline`、`filmOptions`、`onInit`
- `shotList()`：给 rq.py 读。
- `bloom()`、`cornerTag()`

`initFilm` 时会对镜头重叠和空洞给出 console 警告。

**实测**：
- 示例 10 秒，三个镜头（标题、有状态粒子拖尾 + 溶解、画板里的鹈鹕）。snap、contact、render 和 rq 都跑通，渲染 140–200 ms/帧。
- 和旧示例 `scene.js`、`demoscene_intro_scene.js`、`motion_demo_scene.js` 同页加载，没有命名冲突。

**已知局限**：
- 镜头按 `shot()` 调用顺序排，不自动排序。
- 交叉溶解只和**前一个**镜头做。
- 时间表要自己生成（口播对齐脚本的输出），骨架只负责读。

## 6. 有状态镜头：syncState（在 shots.js 里）

**用途**：粒子、拖尾、数据混合这类「每帧在上一帧基础上画」的镜头。跳着取帧（snap、contact、分段渲染、溶解时重画上一个镜头）也和顺序渲染逐像素一致。

**写法**：`state: { init(), step(f, lt), snapshot?(), restore?(snap), every?: 30, maxSnaps?: 40 }`
- 骨架在 draw 之前自动调用 `syncState(shot, f)`：从镜头起点按帧号重放到当前帧。
- 提供 `snapshot`/`restore` 时，每 `every` 帧存一份快照；往回跳时从最近的快照接着算。
- 旧写法 `flow:`，加上 draw 里手动调用 `syncState(this, f)`，仍兼容。

**实测**（示例的粒子镜头，2500 粒子带全屏拖尾）：
- 顺序渲染到 f150，然后**往回跳**到 f130，和顺序渲染的 f130 逐像素相同（平均差 0.000，最大 0），用时 0.7 秒。
- **新页面直接跳**到 f150：同样逐像素相同，0.7 秒。

**已知局限**：
- 没有快照时，跳到长镜头后段要从头重放（每帧一次 step 的代价）。
- 快照要自己深拷贝：数组用 `slice()`，画布用 `getImageData`。1080p 一张约 8MB，所以 `maxSnaps` 默认 40。

## 7. rq.py：并行分段渲染

**用途**：把 a..b 切成段，同时开几个 render.js，断点续跑，最后自动 concat 成一条。

**命令**：
```bash
python3 rq.py 0 60                                   # 每段 8 秒、2 路并行 → render_out/full.mp4
python3 rq.py 0 60 --chunk 6 --workers 3 --out ../render/a1 --name act1.mp4 --check
python3 rq.py 0 60 --plan                            # 只看分段计划
python3 rq.py 0 60 --splits 12.5,30                  # 额外强制断点
```

**规则**：
- 切点对齐帧格，从页面的 `shotList()` 读镜头表，不切在有状态镜头（`state`/`flow`/`solid`）中间。
- 后一个镜头交叉溶解时，不可切范围延伸到溶解结束。
- 短于 1/3 段长的碎段并进相邻段。
- 每段有 `.done`（内容是帧数），帧数对得上就跳过。
- 拼好后用 ffprobe 核对总帧数；加 `--check` 会接着跑 motion_check。

**示例输出**：
```
rq: 0.0–10.0s（f0–f300），镜头 3 个，其中不可切 1 段；分 3 段，2 路并行
  不可切：f108–f201（3.60–6.70s）shots_scene.js:44
  段 c_000000：f0–f108   段 c_000108：f108–f201   段 c_000201：f201–f300
  c_000000 ok  17s（158 ms/帧） …
拼好 render_out/full.mp4：300 帧（应为 300），总用时 26s
```

**实测**：
- 10 秒示例 2 路并行 26 秒，单进程 render.js 28 秒。在 2 核机器上并行几乎不提速：Chromium 单进程已经用满两核，每段还要多启动一次浏览器。300 帧不重不漏，拼接处 motion_check 没有误报切镜头。rq.py 在本机的价值是断点续跑、不切开有状态镜头、自动拼接；多核或有显卡的机器上并行才真正提速。
- 删掉一段的 `.done` 重跑，只重渲那一段（12 秒）。
- 旧式 scene.js（没有镜头表）按 `--chunk` 均分。

**已知局限**：
- 读镜头表要启动一次浏览器（约 2 秒）。
- 并行数受 CPU 限制：2 核机器上开 2 路和单进程差不多快；核数 ≥4 时按「核数 ÷ 2」开。
- 改了画面后旧的 `.done` 不会自动失效，要手动删。

## 8. lib.js：smoothTrack()（相机 / 参数平滑）

**用途**：成片里文字之城上下抖，是因为相机高度每帧按脚下地形最高点算。`smoothTrack(fn, t0, t1, {dt, maxWin, win, passes})` 把逐帧会跳的量预先采样，取滑动最大值（可选），再多遍平滑，返回平滑的 t → 值 函数。它是懒计算、确定性的。

**用法**（lib.js 注释里有完整的相机高度例子）：
```js
const camClear = smoothTrack(t => maxGroundAround(camPath(t)) + 4, 0, 82, { dt: .1, maxWin: 3, win: 1, passes: 4 });
cam.y = Math.max(cam.y, camClear(lt));
```

**实测**（带台阶的地形最高点，4 秒）：

| 设置 | 帧间二阶差（越小越平滑） | 低于原值 |
|---|---|---|
| 原始（不平滑） | 28.6 | — |
| `maxWin 1.2, win .4` | 0.15 | 最多 2.7 |
| `maxWin 3, win 1` | 0.001 | 最多 0.07 |
| 不取最大值 | 0.39 | 低 40+ |

示例里车轮高度也用它平滑（不取最大值）。平滑前 motion_check 报「每 9 帧大跳变」，平滑后不报。

**已知局限**：
- 只能高不能低的量需要 `maxWin ≥ 2·win·√passes`，并再加一点余量。
- 区间外按端点值。

## 9. 布局与线宽：centerIn / measureDraw / pelicanBBox / screenLW / minLW

**用途**：
- 成片里鹈鹕没在画板正中：位置是全局常量。现在可以按实际绘制范围居中。
- 小鸟翅膀断线：`lineWidth .1` 再缩放。现在线宽按屏幕像素算。

**接口**：
- `measureDraw(drawFn, probe, key)`：画一次扫出包围盒（约 30–60 ms，按 key 缓存）。
- `centerIn(ctx, drawFn, [x, y, w, h], {fit, pad, align: 'bottom', key, bbox})`：把 drawFn 画的东西居中（或等比缩放）放进框里。注意第一个参数是 ctx。
- `pelican()` 现在**返回**屏幕包围盒（原来返回 undefined，参数全部兼容）。`pelicanBBox(x, y, s, o)` 不画只算。
- `screenScale(ctx)`、`screenLW(ctx, px)`、`minLW(ctx, lw, px = 1.5)`。
- `pelican` 新增选项 `minPx`（默认 1.5）：所有线条在屏幕上至少 1.5 像素。

**实测**：
- `pelicanBBox` 和像素实测的包围盒，在默认、wheel 1.6、lw 14、两种翻车上误差 ≤3px。整体倾斜的翻车版按外接框算，偏大、偏保守。
- `lw: .4` 缩小到 0.17 倍的鹈鹕：`minPx: 0`（旧行为）辐条和车架是断续的浅灰线，默认的 1.5px 是完整的实线。
- 正常参数下外观不变：默认线宽本来就 ≥1.5px。

**已知局限**：
- `measureDraw` 只看不透明像素，阴影和辉光会把框撑大。
- `pelicanBBox` 是按造型参数算的，自己改了造型要同步改它。

## 10. subs.py：双语字幕

**用途**：剧本 + 逐句时间表 → 中文分条 → 双语 ASS（中文 58px 在上、英文 36px 在下，半透明底框，淡入淡出）+ 中 / 英 / 中英三份 SRT + 给 sub_check 用的 JSON。

**分条规则**（照搬 timeline.py）：
- 标点优先。
- ≤17 字为一条；超过 20 字用 jieba 只在词边界断，不拆《》和 `--terms`。
- 间隔 <1 秒的条合并，每条至少显示 0.9 秒。

英文从「中文条 → 英文」字典读（`.json`，或 Python 文件里的 `EN = {...}`，只做字面量解析、不执行）。缺的条目全部列出、写 `<out>_missing_en.json` 模板，并以退出码 1 退出。

**命令**：
```bash
python3 subs.py script.txt timeline.json en_subs.py --out subs/film --terms "莱恩·莱,Monster Movie,演示场景" --fix "难辩=难辨" --words words.json
```

**实测**（成片真实数据：104 句剧本、`timeline.json` 的 lines、`align/en_subs.py`）：
- 带 `--words`（由 `align/asr_*.json` 换算的逐句词级时间）：生成 202 条，和成片 `timeline.json` 的 subs 逐条文本、起止时刻**完全相同**。`_zh_en.srt` 和成片的 `subs_zh_en.srt` **逐字节相同**；ASS 只有个别结束时刻差 0.01s（舍入）。
- 不带 `--words`（按字数比例估时）：有 16 条因「<1 秒合并」的判断不同而切法不同，工具正确列出了这 16 条缺英文的键。
- 用时 0.7 秒（jieba 加载占大头）。

**已知局限**：
- 英文字典的键必须和切出来的中文条完全一致。换了时间来源或改了剧本，切法会变，要按缺失清单补。
- 含空格或符号的专有名词（如 `Monster Movie`）用占位符保护，其余靠 jieba 词典。
- 「」引号目前允许跨条，sub_check 会报出来。

## 11. sub_check.py：字幕质检

**用途**：报四类问题（详见文件开头）：
- 超长行
- 词中间断开（含《》「」不成对、专有名词被拆、英文词和数字被拆）
- 字幕和口播时间错位
- 英文缺行或没翻

支持双语 ASS、双语 SRT、中英两个 SRT。

**命令**：
```bash
python3 sub_check.py subs.ass --lines timeline.json [--script script.txt] [--terms ...]
python3 sub_check.py subs_zh.srt --en subs_en.srt --lines timeline.json
```
有问题时退出码 1。

**词中间断开的判据**：切点不在 jieba 词边界上，并且「强行断开」让最优分词的对数概率下降 ≥4.5，才报；英文词、数字中间断开一律报。有 `--script` 时，原文在切点处有标点的直接放过。实测断开代价：

| 切点 | 代价 | 判定 |
|---|---|---|
| 电\|影 | 9.3 | 报 |
| 慕尼\|黑 | 18.8 | 报 |
| 儿\|子 | 7.6 | 报 |
| 镜子转\|盘（原文有逗号） | 4.0 | 不报 |
| 停下来\|说 | 2.2 | 不报 |
| 意外里\|长出来 | 0.2 | 不报 |

**实测**：
- **成片的 subs.ass**（202 条）：报 3 条，都是真的。
  - #196/#197 把「“用演示场景的风格做个 10 秒片头”」的引号拆到两条里。
  - #102「他和朋友上线了一个网站」每秒 9.5 字，略快。
  - 没有误报。早期只用分词边界判断时有「转|盘」「里|长」两条误报，改成断开代价后消失。
- **故意做坏的一份**（一处词中间断开、一处 26 字超长、连续 5 条推后 1.2 秒、一条没英文、一条没翻、删掉一条）：全部报出。
  - 推后：报了「比口播早」「晚出现」「重叠」「句尾没有字幕」。
  - 删掉的那条：报了「口播 1.55s 后才出现字幕」。
- **模拟「长句在词中间断开」**（每句机械地每 12 字一切，129 个切点）：
  - 跨了 jieba 词的 63 个里报出 49 个，含全部英文词被拆（Shadertoy、OpenAI、Claude、SKILL）。
  - 没报的多是代价 3–4.4 的弱组合（一只、做成、学会）和词典里没有的人名（普拉托；把人名加进 `--terms` 即可）。
  - 落在词边界上的 169 个都没报。
- 用时约 0.6 秒。

**已知局限**：
- 没有剧本时，被 subs.py 去掉的句中标点处偶尔会误报（代价 ≥4.5 的才会，实测 0 例）。
- 「时间错位」依赖时间表准确；用口播对齐的结果，不要用估算值。
- 阅读速度按每秒 9 个阅读单位（一个汉字或一个英文词）算，是经验值。
